# AIエージェントの不自然な用語生成を抑える指示設計計画

- 作成日: 2026-07-29
- 基準コミット: `ef6276a2b020f32cfa2e0e958b11ea99342ad8ad`
- 状態: 計画レビュー待ち
- 対象: AIコーディングエージェントが回答中に使うjargon、内輪語、不自然な日本語訳、造語
- 非目的: 本書本文に含まれる既存の英語・カタカナ語の章横断監査

## 1. 目的

AIコーディングエージェントは、英語圏のソフトウェア開発で使われる表現を説明なしに
持ち込んだり、定着していない日本語訳をもっともらしく作ったりすることがある。
プログラミング初心者は、それが標準的な専門用語なのか、特定のコミュニティだけで
通じる表現なのか、モデルがその場で作った訳語なのかを判別しにくい。

この問題を完全に防ぐ方法としてではなく、発生を減らし、発生後に気づきやすくする
指示設計として解説する。読者が次の3段階を使い分けられる状態を目標とする。

1. プロジェクト設定ファイルへ言語方針を常設する
2. 文章生成を依頼するとき、対象読者と用語の扱いをプロンプトで指定する
3. 出力後、怪しい用語だけを再確認・修正させ、人間が最終判断する

## 2. 扱う問題

次の3種類を区別して説明する。

| 種類 | 例 | 問題 |
|---|---|---|
| 未説明のjargon | `scaffold`、`happy path`、`guardrail` | 初心者には意味が分からず、検索語も判断できない |
| 不自然な直訳 | 英語の多義語を文脈に合わない日本語へ固定する | 原語との対応や技術的意味が分からなくなる |
| その場で作った訳語 | 一般に定着していない日本語名を標準用語のように使う | 実在する用語だと誤認し、検索や共同作業を妨げる |

外来語や専門用語をすべて避けることは目標にしない。API名、ライブラリ名、解析手法名、
データ形式名など、正確性と検索可能性のために原語が必要なものは残す。問題は、
必要性のない内輪語、初出説明の欠落、定着していない訳語を断定的に使うことである。

## 3. 掲載場所

### 3.1 §0-3 プロジェクト設定ファイル

中心となる解説は
[§0-3 プロジェクト設定ファイル](../../chapters/00_ai_agent.md#0-3-プロジェクト設定ファイルclaudemd--agentsmd)
へ追加する。

この節は、プロジェクト全体で繰り返し守らせたい規約を `CLAUDE.md` または
`AGENTS.md` に記述する場所である。言語方針を毎回の依頼に書くより、設定ファイルへ
常設する方法を最初に示す。

既存の設定例の直後に、次の趣旨の「説明と言語」方針をコピー可能な直接引用として
追加する。設定例のコードブロック自体は変更しない。

- 日本語で、想定読者の知識水準に合わせて説明する
- 開発者コミュニティ内のjargonや略語は、必要な場合だけ使い、初出時に説明する
- 定着した日本語訳を確認できない技術用語について、新しい訳語を作らない
- 日本語訳に確信がない場合は、原語を残して意味を平易な日本語で説明する
- 同じ概念には同じ表記を使う
- 回答前に、不自然な造語や直訳調がないか用語だけを見直す

また、既存の「やってほしいことより、やってはいけないことの方が効果的である」という
記述は、禁止だけを推奨しているように読める。禁止事項を明確にしたうえで、
望ましい代替動作も併記する、という説明へ調整する。

### 3.2 付録D

[付録D](../../chapters/appendix_d_agent_vocabulary.md)には、既存の用語一覧を
書き換えるのではなく、新しい「不自然な用語を減らす指示」節を追加する。

ここでは、エージェントが使う語を理解する既存のD-1〜D-4に対し、ジャーゴン
（jargon）の意味と、不要な語を出力させにくくする実践方法をD-5として示す。
READMEの付録Dの範囲表記もD-1〜D-5へ更新する。

### 3.3 §21の既存記述

`chapters/21_collaboration.md` の「技術的なjargonを避けた平易な説明」という記述は、
非専門家への報告という文脈に限定されており、今回の中心的な解説場所にはしない。
§0-3と付録Dへの導線が必要かだけを実装時に確認し、重複説明は追加しない。

## 4. 掲載するプロンプト

少なくとも次の3種類を、コピーして使える直接引用形式で掲載する。

### 4.1 常設する言語方針

`CLAUDE.md`／`AGENTS.md`に置ける短い規約として、コードブロックではなく
直接引用で示す。ツール名に依存しない内容にし、どちらの設定ファイルでも
同じ方針を使えるようにする。

盛り込む条件は次のとおりである。

1. 対象読者を明示する
2. jargon・略語は必要な場合だけ使う
3. 定着していない日本語訳を新造しない
4. 訳語に確信がなければ原語を残す
5. 原語を残す場合は、一文の平易な説明を添える
6. 最終回答前に用語の一貫性を確認する

### 4.2 文章生成時の追加指示

README、解析報告、コードレビュー、説明文などを生成させる依頼の末尾に付けられる
短い追記として示す。

「専門用語を使わない」だけでは、必要な技術用語まで曖昧な表現へ変わるおそれがある。
そのため、残す語と避ける語を分けて指定する。

- 正式な製品名、API名、遺伝子名、解析手法名は変更しない
- 初心者に不要な内輪語は平易な日本語へ直す
- 定着した日本語訳が不明なら、無理に訳さず原語と説明を併記する
- 科学的・技術的意味を推測で単純化しない

### 4.3 出力後の用語レビュー指示

すでに得た回答に怪しい用語が含まれる場合の修正指示を示す。

修正時には全文を自由に書き直させず、次の順序を指定する。

1. jargon、略語、不自然な直訳、定着していない可能性のある訳語を抽出する
2. 各語について「定着語」「説明が必要」「原語を残す」「置換」のいずれかを判断する
3. 判断に自信がなければ断定せず、公式ドキュメントで使われる原語を示す
4. 技術的意味を変えずに対象箇所だけを修正する

この指示は、エージェント自身の再確認だけで正しさを保証するものではない。最終的には
人間が公式ドキュメント、論文、所属分野の慣用表記と照合する必要がある。

## 5. 説明上の要点

### 5.1 「禁止」だけでなく代替動作を指定する

「jargonを使わない」「変な日本語を書かない」という否定だけでは、何をすべきかが
曖昧である。次の代替動作を明示する。

- 分からない語を消すのではなく、必要なら原語を残して説明する
- 訳語を作るのではなく、確信がないことを示す
- 専門用語を一般語へ置き換えるのではなく、初出時に短く定義する

### 5.2 一度の指示で完全には防げない

モデルやバージョン、会話の文脈によって出力は変わる。プロンプトは発生確率を下げる
手段であり、用語の正しさを保証する検証機構ではない。この限界を明記し、
「生成→用語レビュー→人間の確認」という役割分担を示す。

### 5.3 原語を残すことを失敗とみなさない

自然な日本語訳がない技術用語は多い。無理に日本語化するより、検索可能な原語と
短い日本語説明を併記する方が安全な場合がある。本書の初出表記規約
「日本語（英語）」とも整合させる。

## 6. 根拠の確認

実装時には、Claude CodeとCodexの双方に適用できる一般的な指示として記述する。
次の点は、各社の最新の公式プロンプトガイドで確認する。

- 指示を明確かつ具体的に書くこと
- 対象読者、文脈、出力形式を与えること
- 期待する出力例または判断手順を示すこと
- 永続的なプロジェクト指示と、その場の依頼を使い分けること

公式資料が直接述べていない効果を、保証された機能として書かない。モデルが
非標準の訳語を生成するという問題は観察される失敗例として扱い、プロンプトによる
対策は緩和策と表現する。本文へ事実や仕様を追加する場合は、章の参考文献と
`references/ch00.bib`を同期する。

## 8. 検証と完了条件

### 8.1 検証

1. `git diff --check`
2. 構造規約チェック
3. 相互参照チェック
4. 新しいプロンプトが直接引用形式でコピーできることの目視確認
5. Claude Code・Codexのどちらか一方にだけ依存する表現がないことの確認
6. EPUB生成とEPUBCheck
7. CIの既存テストとruff検査

プロンプト例は、数種類の説明依頼で試し、不要なjargonを減らしつつ正式名称と
技術的意味を維持できるかを確認する。ただし、非決定的な出力を合否判定する
自動テストにはしない。

### 8.2 完了条件

次をすべて満たした時点で完了とする。

1. §0-3に、プロジェクト設定ファイルへ常設できる言語方針がある
2. 付録Dに、単発の生成指示と出力後のレビュー指示がある
3. 訳語に確信がない場合は原語を残す、という代替動作が明記されている
4. プロンプトでは完全に防げず、人間が最終確認する必要があると説明している
5. `TODO.md`のjargon関連2項目が、実装内容と対応した状態で完了している
6. 構造・相互参照・EPUB・CIの検証が成功する

## 9. コラムHTMLアンカーとの分離

コラムHTMLアンカーは文章内容を変更しない体裁作業である。本計画と同じPRには含めず、
jargon・不自然な用語生成への指示を実装した後、別ブランチ・別PRで対応する。
