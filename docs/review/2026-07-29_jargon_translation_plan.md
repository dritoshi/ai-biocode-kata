# jargon・不自然な翻訳語の整理計画

- 作成日: 2026-07-29
- 基準コミット: `ef6276a2b020f32cfa2e0e958b11ea99342ad8ad`
- 状態: 計画レビュー待ち
- 対象: `chapters/*.md` の読者向け本文、および用語表記に関係する `README.md`
- 非目的: 技術内容の追加、コード例の変更、単なる好みによる全面的な文章の書き換え

## 1. 目的

本書はプログラミング初心者の実験系生命科学者を対象としている。一方、本文には、
AIエージェントやソフトウェア開発の文脈で使われる英語、カタカナ語、英語からの
直訳調の表現が含まれる。定着した専門用語まで平易な語へ置き換えると正確性や
検索可能性を損なうが、説明のないjargonや不自然な訳語を残すと初心者の理解を妨げる。

本計画では、次の状態を目標とする。

1. 定着した技術用語、固有名詞、コード上の名称は維持する
2. 初心者に説明が必要な語は、初出時に日本語と英語または略称を対応付ける
3. 日本語で自然に表せる不要なjargonは、意味を変えずに平易な表現へ直す
4. 英文の語順や語義を引きずった不自然な訳文は、技術的意味を保って日本語として整える
5. AIエージェントへ文章作成を依頼するとき、対象読者と用語の扱いを具体的に指定できる

## 3. 判定基準

候補は語そのものではなく、使われている文脈で判定する。

| 判定 | 内容 | 対応 |
|---|---|---|
| J0 | 定着した専門用語、固有名詞、正式なUI・API・コマンド名 | 原則として変更しない |
| J1 | 必要な専門用語だが、初出説明や日本語との対応が不足 | 初出説明または参照リンクを補う |
| J2 | 日本語で自然に表せる、説明のない英語・カタカナ表現 | 平易な日本語へ置き換える |
| J3 | 英文の語順・語義を引きずり、日本語として不自然または意味が曖昧 | 文単位で自然な日本語へ直す |
| J4 | エージェントの発話例や付録Dで、理解対象として意図的に提示した語 | 語は残し、意味と注意点を説明する |
| JN | コード、識別子、引用、文献名など本文の言い換え対象ではない | 対象外 |

### 3.1 変更しないもの

- コードブロック、インラインコード、コマンド、オプション、ファイル名
- 遺伝子・タンパク質名、データ形式名、製品・サービス・ライブラリの正式名称
- APIやUIに実際に表示される名称
- 引用文、論文・書籍・Web文献の原題
- 初出説明があり、その後の使用が読者の検索にも有用な定着済み専門用語
- 付録Dで「エージェントが実際に使う表現」として意図的に示す見出し語

### 3.2 修正候補にするもの

- 日本語だけで意味を十分に伝えられるのに、英語やカタカナ語だけで表した箇所
- 同じ概念に複数の訳語が混在し、別概念に見える箇所
- 原語の多義性をそのまま移し、日本語では意味が特定できない箇所
- 主語・修飾関係・否定範囲が英語の語順に引かれて読みにくい箇所
- 「実行する」「提供する」「サポートする」など、対象や動作が曖昧な直訳調の動詞
- 初心者向け説明の中で、未定義の略語や開発者コミュニティ内の俗語を使う箇所

「カタカナ語である」「英語を含む」という理由だけでは修正しない。たとえば
API、コンテナ、ワークフローのように本書の学習対象であり、検索時にも必要な語は
J0またはJ1とする。

## 4. 監査方法

### 4.1 機械抽出

次の検索結果を候補リストの入口として使う。

- 本文中の裸の英単語・英語句
- カタカナ語に「する」「実行する」などを付けた表現
- 付録Dのカタカナ動詞・名詞と同じ語
- 同じ英語に対する複数の日本語表記
- `jargon`、`scaffold`、`spike`、`happy path` などエージェント固有の頻出語

Markdownを壊さないため、コードフェンス、インラインコード、URL、引用文献の原題は
機械抽出後に除外する。機械抽出結果をそのまま一括置換には使わない。

### 4.2 人手による文脈レビュー

各章を見出し単位で読み、次の2巡を行う。

1. **用語巡**: J1・J2・J4を判定し、初出説明、表記統一、付録Dへの導線を確認する
2. **日本語巡**: J3を判定し、主語、修飾関係、動詞、否定範囲を確認する

指示例、表、図のキャプション、コラムも対象に含める。コードと参考文献情報は
対象外とする。バイオインフォマティクス用語は平易化によって意味を変えないよう、
章内の定義と公式用語を優先する。

### 4.3 findingの記録

監査結果は `docs/review/jargon_translation_findings.csv` に記録する。

| 列 | 内容 |
|---|---|
| `id` | `JARGON-NNNN` 形式の一意なID |
| `file` / `line` | 対象位置 |
| `classification` | J1〜J4 |
| `severity` | `high` または `medium` |
| `current_text` | 現行表現 |
| `proposed_text` | 修正案 |
| `reason` | 初心者にとっての問題と修正根拠 |
| `status` | `open`、`fixed`、`wont_fix` |

意味が変わる、または誤解を招く候補を `high`、初心者の理解を妨げる未定義語、
表記揺れ、直訳調を `medium` とする。単なる好みの差はfindingにしない。
用語の正式性に疑義がある場合は、公式ドキュメントまたは当該分野の一次情報を確認し、
確認先を `reason` に記録する。

## 5. 実装順序

### 5.1 基盤修正

最初の実装PRでは、監査全体の基準になる次の3点を修正する。

1. 付録Dに「ジャーゴン（jargon）」を追加し、限られた集団内で通じる専門的・俗語的な
   表現であることを説明する
2. `chapters/21_collaboration.md` の裸の `jargon` を、日本語の意味が先に分かる表記へ直す
3. §21-3の「エージェントへの指示例」に、対象読者、残す専門用語、初出説明、
   避ける表現を指定する再利用可能な指示例を追加する

指示は「専門用語をすべて使わない」とはしない。遺伝子名、解析手法名、統計用語など
正確性に必要な語は残し、初出時に短く説明するよう求める。不自然な直訳を避けることと、
科学的意味を推測で平易化しないことも明記する。

### 5.2 章横断の修正

基盤修正後、findingを章順に実装する。1PRの本文変更をレビュー可能な量に保つため、
原則として1PRあたり25件以下とする。findingが25件以下なら1PRにまとめ、超える場合は
次の章群を境界として分割する。

1. はじめに・§0〜§5
2. §6〜§11
3. §12〜§17
4. §18〜§21・付録・用語集・README

単純な語の置換でも文脈を1件ずつ確認する。段落全体を書き換える必要がある場合は、
技術的主張、引用、相互参照、コードとの対応を変更していないことを差分レビューする。

### 5.3 TODOの完了

基盤修正と章横断監査が完了してから、`TODO.md` の次の項目を完了扱いにする。

- jargonを減らす指示
- 付録Dのjargon項目

監査途中ではチェック済みにしない。

## 6. 検証

各実装PRで次を確認する。

1. `git diff --check`
2. 太字内カッコ・数式・相互参照を含む構造検査
3. 章間・節間リンクの検査
4. コードフェンス内に意図しない変更がないことの差分確認
5. 用語の初出表記と、付録D・用語集への導線の確認
6. EPUB生成とEPUBCheckによるMarkdown/HTML変換結果の確認
7. CIの既存テストとruff検査

コード例を変更しないため、`scripts/` と `tests/` は本作業の変更対象にしない。
監査中にコード例の問題を見つけても、この作業へ混ぜず別findingとして記録する。

## 7. レビューと完了条件

各PRでは、修正者による確認とは別に次の観点でレビューする。

- 専門用語を平易化しすぎて意味を変えていないか
- 英語を日本語へ置き換えただけで、かえって検索しにくくしていないか
- 日本語として自然でも、元の技術的主張を強めたり弱めたりしていないか
- 初心者向け説明が増えすぎて、同じ定義を各章で重複させていないか
- コード、UI、API、引用の原表記を誤って変更していないか

対象範囲を2巡した後、未解消の `high`・`medium` findingがなくなるまで再確認する。
J4は説明付きで意図的に残せる。
次をすべて満たした時点で完了とする。

1. `jargon_translation_findings.csv` に `open` がない
2. 付録Dで `jargon` の意味を引ける
3. §21に対象読者と用語の扱いを指定する指示例がある
4. findingに挙がった英語・カタカナ語をJ4として残す場合、その理由を記録している
5. 構造・リンク・EPUB・CIの検証が成功する

## 8. コラムHTMLアンカーとの分離

コラムHTMLアンカーは文章内容を変更しない体裁作業であり、本計画のPRには含めない。
jargon対応を完了した後、別ブランチ・別PRで行う。

後続作業では、現在検出できる18章・64コラムを正本として再監査し、ASCIIで重複しない
安定したID命名規則を決める。各コラム直前に `<a id="..."></a>` を挿入し、本文の語句、
見出し、引用記法は変更しない。GitHub、EPUB、PDFでリンク先が機能することを確認する。
