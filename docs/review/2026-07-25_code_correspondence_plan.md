# 本文コード ↔ `scripts/` 対応表 作成計画

- **作成日**: 2026-07-25
- **版**: 第6版（第0版10・第1版8・第2版6・第3版5・第4版2・第5版2の findings を反映）
- **状態**: **レビュー収束**（第6版の点検で新規 findings ゼロ）
- **成果物**: 対応表（Markdown + JSON）と修正案。**本文・`scripts/` の実体は変更しない**

## 0. この計画が必要な理由

同一セッション内で、本文と `scripts/` の乖離について3回続けて誤った測定・結論を出した。

| 回 | 主張 | 実際 |
|---|---|---|
| 1 | 「本文の31%が `scripts/` に無い」 | 照合先から `tests/`・サブディレクトリ・非Pythonを漏らしていた。実際は17% |
| 2 | 「乖離の正体は ruff format による整形差」 | §11 の1例からの一般化。全体では74件中2件のみ |
| 3 | 「抜粋にすると2.69倍に膨らむ」 | 「該当関数まるごと」を測っており、抜粋の定義を取り違えていた |

いずれも**少数例からの一般化**と**測定単位の取り違え**が原因である。したがって本計画は、
結論より先に**判定方法そのものの妥当性を検証する手順**を組み込む。

第0版の自己レビューでもさらに10件の欠陥が見つかった（付録A）。特に重大だったのは、
**構造的等価性と振る舞い等価性という直交する2軸を1本の階段に混ぜていたこと**と、
**「抜粋」を表現する関係が無かったこと**である。本タスクの主題が抜粋の可否であるにもかかわらず、
それを表せない設計になっていた。

## 1. 目的と非目的

### 目的

本文のコード片と `scripts/`（および `tests/`）の実体の対応関係を、次の観点で網羅した表を作る。

1. **多対多の対応** — 1つのスクリプトに複数の本文ブロックが対応する、逆に1ブロックが複数スクリプトにまたがる
2. **片側のみに存在** — 本文にしかない / `scripts/` にしかない
3. **片側だけが更新された疑い** — 対応関係はあるが内容が食い違う
4. **本質的な同一性** — 整形・コメント・docstring の差に惑わされない判定
5. **テストの有無と成否** — 対応する `scripts/` 側にテストがあるか、それは通るか

### 非目的（やらないこと）

- 本文（`chapters/`）の修正
- `scripts/` `tests/` の実体の修正
- 検証ツールの本採用（`scripts/review/` への追加）

> 分析スクリプトは scratchpad に置き、リポジトリにはコミットしない。
> 成果物は `docs/review/` 配下の対応表と修正案のみ。ツールの本採用が有益と判断したら、
> 修正案の中で別タスクとして提案する。

## 3. 対応の単位

過去の失敗はすべて「ブロック ↔ ファイル」という粗い単位に起因する。本計画では**2層**で持つ。

### 3-0. 対象範囲（第3版で欠落していた定義）

**本文側**: `chapters/NN_*.md`（番号付きの章ファイル）のみ。

- **付録・はじめに・用語集は対象外**（`appendix_*.md` `hajimeni.md` `glossary.md` `notice.md` `author.md`）。
  対応する `scripts/appendix_*` が存在せず、全件が S8 になって表を汚すため
- ただし**対象外にした事実と、そこに含まれるコードブロック数を成果物に明記する**
  （黙って落とすと「網羅した」と誤読される）

**実体側**: `scripts/chNN/**` に加えて **`tests/chNN/**` を含める**。

> 第3版は実体側を `scripts/` のみとしていたが、**本文はテストコードも載せている**
> （§8 の `conftest.py` やテスト関数の例）。`tests/` を除くと、それらが全て
> 「本文のみ」に分類され、実際には存在するテストとの対応を見落とす。
> 定義の母数は `scripts/chNN` の291 ＋ `tests/chNN` の1007 = **1298**（実測済み）。

`scripts/` 直下のツール（`count_chars.py` 等）と `scripts/review/` は**対象外**。
書籍のサンプルコードではなく制作用ツールであるため。

### 3-1. 定義単位（主）

`ast` で抽出した名前付き定義（`FunctionDef` / `AsyncFunctionDef` / `ClassDef`）を最小単位とする。

- 本文側: `(章, ファイル, 行, ブロック番号, 定義名, 正規化本体)`
- 実体側: `(ファイル, 行, 定義名, 正規化本体, scripts か tests か)`

### 3-2. ブロック単位（従）

定義を含まないブロック（トップレベルの手続きのみ、設定ファイル、Snakefile、断片）は
定義単位に落とせない。ブロック全体を1単位として扱い、定義単位の表とは分けて集計する。

### 3-3. 非 Python 資産の扱い（第0版から具体化）

| 言語タグ | 対応先の探し方 | 比較方法 |
|---|---|---|
| Snakefile（`python` タグ） | `scripts/chNN/Snakefile` | `rule` 名で分割し、rule 単位で行集合を比較 |
| `dockerfile` | `scripts/chNN/Dockerfile*` | 命令（`FROM`/`RUN`/`COPY`）単位に正規化し比較 |
| `yaml` | `scripts/chNN/*.y*ml` | `yaml.safe_load` で構造化し、辞書として比較 |
| `bash` | `scripts/chNN/*.sh` | コメント除去・空白正規化した行集合 |
| `makefile` | `scripts/chNN/Makefile` | ターゲット単位で分割 |

**YAML は構造比較にする**。行順やインデントの差で乖離と誤判定しないため。
`yaml` は標準ライブラリに無いが、`uv run` の環境に含まれるか実装時に確認し、
無ければ行集合比較へ落として**その旨を成果物に明記する**。

## 4. 同一性の判定 — 直交する2軸（第0版の最重要修正）

第0版は構造的等価性と振る舞い等価性を1本の階段にしていたが、**この2つは直交する**。
同名で中身が違っても（構造的に違う）テストは通る（振る舞いは同じ）ことがあり、
逆に構造が同じでも実行できないことがある。**2つの独立した列**として持つ。

### 4-1. 構造軸（S）

上から順に試し、最初に当たった段階を採る。

| 段階 | 判定 | 方法 | 閾値 |
|---|---|---|---|
| **S0** | 完全同一 | `ast.unparse` 正規化後が一致 | 不要 |
| **S1** | docstring のみ差 | docstring を除いて正規化し一致 | 不要 |
| **S2** | 局所名リネームのみ差 | 局所名をα変換して一致 | 不要 |
| **S3** | **定義名のみ差** | 定義名を伏せると一致 | 不要 |
| **S4** | **本文が実体の抜粋** | 本文側の文の並びが実体側の**順序保存の部分列** | 不要 |
| **S5** | **実体が本文の抜粋** | 逆向きの包含 | 不要 |
| **S6** | 同名・内容差 | 名前一致、S0〜S5 いずれも不成立 | 不要 |
| **S7** | 別名・構造類似 | 構造フィンガープリントの類似度 | **要**（9-1） |
| **S8** | 対応なし | 片側のみに存在 | — |

> **S4/S5 が第0版に欠けていた**。本タスクの主題は「本文を実体の抜粋にできるか」であり、
> それを表せない設計だった。部分列判定は**順序を保った包含**で行い、集合の包含では代用しない。
> 集合包含は順序を無視するため、既存ツールの偽陰性の原因になっている。
>
> **S3 が第1版に欠けていた**。「定義名だけ違い中身は同一」は閾値なしで厳密に判定できるのに、
> 閾値依存の S7 に落ちる設計だった。`filter_reads_generator` と `filter_by_length` のような
> 改名の検出は本タスクの要求（多対多・片側更新）に直結するため、独立した段階にする。

**S0〜S6 は閾値を持たない**。閾値を要するのは S7 のみで、その決め方は 9-1 に定める。

#### S4/S5 の判定と「散らばり」の記録

部分列判定は `difflib.SequenceMatcher` の一致ブロックが短い側を完全に覆うかで行う。
ただし**覆えるだけでは抜粋とは言えない**。実体の200行に飛び飛びで散らばった10行を拾っても
形式上は部分列になる。次の2つを**閾値ではなく指標として併記**し、人間が判断できるようにする。

- **断片数**: 一致ブロックの個数（1なら完全に連続した抜粋）
- **スパン**: 実体側で最初の一致行から最後の一致行までの行数

「断片数1・スパン=本文行数」が理想的な抜粋であり、断片数が多いほど「拾い集め」に近い。

#### 1つの本文定義が複数の実体定義に対応する場合（第2版で欠落）

「多対多を扱う」と謳いながら、S0〜S8 は**1対1のペアしか表せない設計**だった。
実際には本文の簡略版1つが実体では複数関数に分割されていることがある
（§17-772 の `count_long_sequences` は実体では `read_fastq_records` と
`filter_by_length` に分かれている可能性がある）。

**対処**: S4/S5 の判定を2段構えにする。

1. まず**単一の実体定義**に対して部分列判定を行う
2. 失敗した場合、**同一ファイル内の実体定義を出現順に連結したもの**に対して再度判定する
3. 当たった場合は S4/S5 のまま扱い、**対応先の個数**を記録する（`対応先: 2定義`）

対応先が複数のとき、その関係は「分割」または「統合」である。表の備考に明記する。

### 4-1-2. 比較するペアの生成（第1版で欠落）

145 × 1298 の総当たりは無駄が多く、また「どのペアを比べたか」が不明確だと結果を検証できない。
**ハッシュ索引で候補を生成する**手順を定める。

1. 実体側の全定義について、4種の正規化キーを計算し索引を作る
   - K0: 正規化そのまま / K1: docstring 除去 / K2: K1 + α変換 / K3: K2 + 定義名を伏せる
2. 本文側の各定義について K0→K3 の順に索引を引く。**当たれば S0〜S3 が O(1) で確定**する
3. 索引で当たらなかったものについてのみ、次の候補集合と部分列判定（S4/S5）を行う
   - 同名の実体定義（章内・章外の双方）
   - 同一章の全実体定義
4. S4/S5 でも当たらず、同名の相手がいれば S6
5. 残りに対してのみ S7 の類似度計算を行う（同一章内に限定）

**この設計により、閾値を要する計算は最後の少数だけになる**。工程ごとの処理件数を記録し、
成果物に載せる（どの段階で何件確定したかが追える）。

### 4-2. 振る舞い軸（B）

構造軸とは独立に判定する。

#### 適用条件（第1版で不明確）

差し替えて実行できるのは、**本文側が完結した定義を持ち、かつ実体側に同名の定義がある**場合に限る。

| 状況 | B軸 |
|---|---|
| 本文が完結した定義を持ち、実体に同名がある | B0〜B2 を判定 |
| 本文が抜粋（S4）で定義本体が不完全 | **B3（適用不可）**。抜粋は差し替えられない |
| 実体に対応が無い（S8） | B3 |
| 対応するテストが無い | B3 |

| 段階 | 判定 |
|---|---|
| **B0** | 本文版に差し替えても実体のテストが全て通る |
| **B1** | 一部が失敗する（失敗したテスト名を記録） |
| **B2** | 差し替えて実行できない（import 失敗・依存不足） |
| **B3** | 対象外（対応するテストが無い） |

#### 実行手順と安全対策（第0版から具体化）

1. **サブプロセスで実行する**。本文コードを現行プロセスで `exec` しない
2. 作業ディレクトリを scratchpad 内の一時ディレクトリにする（ファイル書き込みの被害を局所化）
3. タイムアウト 30 秒
4. ネットワークアクセスや破壊的操作を含むブロックは**事前パターン検査で除外**し、B2 とする
5. 差し替えの実現方法は次の順で試す。**単純な方から**
   1. **リポジトリを一時ディレクトリへコピーし、対象スクリプトの当該定義を本文版へ置換**して
      その場で `pytest` を走らせる。最も単純で、import 経路の細工が要らない
   2. 1 が困難な場合のみ `conftest.py` による属性置換を検討する
   3. いずれも不可なら **B2（判定不能）** とし、理由を記録する

**B0 の根拠の強さはテストの厚さに依存する**。表には**そのテストの件数を併記**し、
「テスト2件で B0」と「テスト20件で B0」を読者が区別できるようにする。

### 4-3. 時系列軸（T）— 「片側だけ更新された」の検出（第0版で欠落）

ユーザーの要求「一方のみが更新されてしまったもの」は、内容の差だけでは判定できない。
Git 履歴を使う。

- 本文側: `git log --format=%cI -L <block_start>,<block_end>:<chapter>` の**先頭行**で
  そのブロックの行範囲の最終更新を取る（章ファイル全体の日時では粗すぎる）
- 実体側: 同様に定義の行範囲で取る
- 新しい側を「更新された側」の候補として記録する

**実行可能性を確認済み**: 上記コマンドは動作し、1回あたり約 0.016 秒だった。
日時のほかに diff も出力されるため先頭行のみを採る。対象は S6（同名・内容差）に限定する。

## 5. 多対多・片側のみの表現

### 5-1. 多対多

対応は**ペアの集合**として持つ。1つの本文定義が複数の実体定義に対応してよく、逆も許す。
表は2つのビューで出す。

- ビューA（本文起点）: 本文の全定義 × 対応する実体（0..n）
- ビューB（実体起点）: 実体の全定義 × 対応する本文（0..n）

集約として「1スクリプト ↔ 何ブロック」の対応数も出す。

### 5-2. 片側のみ

- **本文のみ**: 実体に無い。読者がリポジトリで確認できないコード
- **実体のみ**: 本文で触れられていない。それ自体は問題ではないため、
  次の基準で**さらに分類**する（第1版では基準が無く、291件を無差別に並べる設計だった）

| 種別 | 判定 | 要対応か |
|---|---|---|
| 図表生成 | ファイル名が `plot_` / `generate_` で始まる | 否 |
| 内部ヘルパー | 定義名が `_` で始まる | 否 |
| デモ・テンプレート | `demo` / `template` / `example` を名前に含む | 否 |
| テスト補助 | `tests/` 配下の定義 | 否 |
| **上記以外** | | **本文で説明すべきものが埋もれていないかの点検対象** |

## 6. テスト情報の取得

### 6-1. スクリプト → テストの対応

3経路で紐付け、いずれかで当たれば対応ありとする。

1. **import 解析**: `tests/**/*.py` から `from scripts.chNN.mod import ...` を抽出
2. **命名規約**: `tests/chNN/test_<stem>.py` の存在
3. **定義名の参照**: テスト本文に当該定義名が現れるか

### 6-2. テストの成否

`pytest <test_file> -q -p no:cacheprovider` を**テストファイル単位**で実行し、
`passed / failed / skipped / errors` を記録する。**skip も必ず記録する**
（cffconvert 未導入でテストが静かに skip していた前例がある）。

**判断基準**（第1版は実装時送りにしていた）: まず1ファイルの実行時間を計測し、
70倍した見積もりが **3分以内なら全ファイル個別実行**、超えるなら次の順で絞る。

1. 対応表に現れるスクリプトのテストのみ個別実行
2. 残りは `pytest tests/ -q` の一括実行結果で代表させ、**絞った旨と対象外の件数を成果物に明記する**

いずれの場合も、全体一括実行を1回行い、`passed / failed / skipped` の総数を基準値として記録する。

### 6-3. 定義レベルのカバレッジ

「その定義にテストがあるか」は 6-1 の経路3で近似する。関数単位の実行カバレッジは取らない。
**近似であることを表に明記する**。

## 7. 判定方法そのものの検証（最重要）

過去3回の誤りを踏まえ、**結論を出す前に方法を検証する**。1つでも不合格なら方法を修正してやり直す。

### 7-1. 金標準（ゴールドセット）— 分類器を走らせる前にラベルを確定する

**第0版の欠陥**: 「実施時に無作為抽出して目視」としており、分類器の出力を見てから
正解を決める循環に陥る余地があった。

**修正後の手順**:

1. 分類器を実装する**前**に、12ペアを人手で読んでラベルを確定し、
   `scratchpad/goldset.json` に書き出して**凍結する**
2. うち5ペアは本セッションで既に内容を確認済みのものを使う（下表）
3. 残り7ペアは**再現可能な手順**で選ぶ。分類器の出力は見ない
   - 母集団: 本文の全定義（実装時に確定）を `(ファイル名, 行)` で辞書順に並べたもの
   - 抽出: `random.Random(20260725).sample(母集団, 7)`。**シードを固定して成果物に記録する**

4. 分類器の出力と突き合わせ、**不一致が1件でもあれば方法を修正する**

|---|---|---|

### 7-2. 負例による検査（偽陽性の確認）

`scripts/` の既存関数を機械的に改変した**偽の本文コード**を作り、
S0〜S5 が「同一」と誤判定しないことを確認する。

- 比較演算子の反転（`>=` → `>`）
- 引数順の入れ替え
- 定数の変更（`0.5` → `0.05`）
- **文の順序入れ替え**（集合ベース判定なら誤って同一と判定される。S4 の部分列判定が
  順序を見ていることの確認になる）

**いずれかを「同一」と判定したら方法を修正する。**

### 7-2-2. 偽陰性の検査（第2版で欠落）

## 8. 既知の限界（成果物に明記する）

1. **振る舞い等価はテストの範囲でしか言えない**。テストが薄い定義では B0 の根拠は弱い
2. **章をまたぐ対応**を既定では見ない（§15 の Snakemake `rule` は `scripts/ch14/Snakefile` が対応）。
   別立てで章横断の候補も出すが、精度は落ちる
3. **非 Python 資産**は正規化の手段が乏しい。YAML 以外は行・命令単位の比較に留まる
4. **どちらが正しいかは判定しない**。S6 は「食い違い」を示すだけで、正誤は人間が決める
5. **時系列（T軸）は行範囲の履歴に依存する**。大規模な章の書き換えがあると精度が落ちる
6. **S3（定義名のみ差）は改名だけでなくコピペ由来の重複も拾う**。実体側に同じ実装の別名関数が
   並んでいれば、それは改名ではなく重複の疑いである。備考でその可能性に触れる
7. **検証ゲートが収束しない場合**（7章の検査を3巡しても不合格が残る）、
   方法の修正を打ち切り、**達成できなかった検証項目を明示してユーザーに判断を仰ぐ**。
   不確かな結果を確からしく見せない

### 10-3. 修正案の型（第3版で未定義）

「優先度つき」とだけ書いており、何を修正案とするかの型が無かった。次の5型に限定し、

|---|---|---|
| **A. 実体を新設** | S8（本文のみ） | 本文のコードを `scripts/` または `tests/` に起こしテストを付ける |

| **E. テストを補う** | B3（テスト無し）・B1（失敗） | 対応するテストの新設・修正 |

優先度は「読者が直接影響を受けるか」で決める。
実体が存在せず読者がリポジトリで確認できないもの（型A）を最優先とする。
