## 3. 調査対象と単位

### 3.1 本文側

対象は番号付き22章の fenced code block 全529件とする。長さ、言語タグ、
構文解析可否を理由に黙って除外しない。

各ブロックに安定したIDを付け、次を記録する。

- 章、開始・終了行、直近見出し、言語タグ
- コード全文のハッシュ
- 種別と、`scripts/` または `tests/` への配置が規約上必要か
- 対応する実体ファイル・定義・行
- 対応の確度、本質的一致の判定、差分要約
- 対応スクリプトのテスト有無と実行結果
- 修正要否と修正案

### 3.2 `scripts/` 側

対象は `scripts/ch00/**`〜`scripts/ch21/**` の全実ファイルとする。
`__pycache__` と `.pyc` は除くが、次は除外しない。

- Python モジュール
- Snakefile、Dockerfile、YAML、シェル、Makefileなどの設定・ワークフロー
- テンプレート、データ、READMEなどの補助資産
- `__init__.py`

Python はファイル、トップレベル文、関数、クラス、メソッドの各単位を持つ。
非Pythonはファイル単位を基本とし、rule、ターゲット、ジョブなど安全に分割できる場合だけ
下位単位も持つ。各ファイルについて本文側の対応が0件でも必ず記録する。

本文対応が0件のファイルは、`図表生成`、`内部ヘルパー`、`デモ・テンプレート`、
`データ・補助資産`、`本文で説明すべき可能性あり`へ分類する。ファイル名だけではなく、
モジュールの目的、公開関数、本文からの間接利用を確認する。

### 3.3 `tests/` 側

`tests/` は二つの役割を分離して扱う。

1. 本文に掲載されたテストコードの対応先
2. `scripts/` のテスト有無・成否を示す証拠

テスト関数を通常のスクリプト実装と同じ母集団へ混ぜない。

### 3.4 本文ブロックの種別

全ブロックを次のいずれかに分類する。判断根拠も記録する。

| 種別 | 実体配置 |
|---|---|
| 実装コード | `scripts/` 必須 |
| テストコード | `tests/` 必須 |
| 設定・ワークフロー定義 | `scripts/` 必須 |
| 悪例・反面教師 | 不要 |
| 演習問題 | 不要 |
| ライブラリの使い方紹介 | 不要 |

| コマンド、出力、データ、図解、疑似コード | 不要 |

見出しだけで決めず、前後の説明とコード内容を読む。たとえば演習内のレビュー対象は
規約上不要であり、「本文のみの欠落」には数えない。

## 4. 対応付けと本質的一致の判定

### 4.1 候補生成

候補は次の証拠を併用して作る。

1. 本文中に明記されたファイル名、import、関数名、クラス名
2. 同じ章番号と同名定義
3. コメントと整形を除いたトークン列
4. Python AST の正規化表現
5. 順序を保った文・命令列の包含
6. ファイル全体の呼出し関係と入出力
7. 章をまたぐ同名・高類似候補

候補生成の類似度だけで対応を確定しない。配置必須の本文ブロックと、
対応ありと判定した全ブロックは最終的に前後の説明と実体を人手確認する。

### 4.2 一致区分

| 区分 | 意味 |
|---|---|
| E0 | コメント・空白を除いて同一 |
| E1 | docstring、説明用コメント、無関係な局所名などを除けば同じ処理 |
| E2 | 本文が実体の矛盾しない抜粋。省略部分と境界を特定できる |
| E3 | 同じ題材・APIだが、入出力、分岐、例外、定数など振る舞いに差がある |
| E4 | 対応候補はあるが、本質的一致を確定できない |
| E5 | 対応なし |
| EN | 規約上、対応不要 |

型注釈は実行時に使われる場合があるため一律に無視しない。定義名変更も再帰参照や
外部APIに影響しうるため、自動的にE1へ落とさず内容を確認する。

E2は「短い側が長い側の行集合に含まれる」だけでは認めない。順序、制御構造、
変数の依存、前後の説明を確認し、削除された部分が本文の主張と矛盾しない場合だけ採用する。

### 4.3 多対多

本文ブロックとスクリプト実体の関係を独立した関係表として持つ。
1ブロックが複数ファイル・定義に対応する場合と、1実体が複数ブロックへ抜粋される場合を
どちらも表現する。JSON配列の先頭1件だけを「正解」とみなさない。

## 5. テストの確認

### 5.1 テスト対応

各スクリプトファイルについて、次の証拠から対応テストを列挙する。

1. `tests/chNN/test_<module>.py` という命名
2. テスト側の import
3. monkeypatch、subprocess、ファイル名参照
4. 対象関数・CLI・設定ファイルの参照

「テストファイルがある」と「当該定義・動作が実際にテストされる」を分ける。
定義単位の確認が静的参照だけの場合は「参照あり（カバレッジ未測定）」と表示する。

### 5.2 実行

1. 現行環境と依存関係を記録する
2. `pytest tests/ -q -p no:cacheprovider` を一括実行する
3. 69個の `test_*.py` をファイル単位で実行し、passed / failed / skipped / errorを記録する
4. skipは理由を確認する
5. 完結した本文実装で安全に差し替え可能なE3候補は、一時コピーで対応テストを実行する

本文コードの差し替え試験は、ネットワーク、外部サービス、破壊的操作を必要としないものに限る。
差し替え不能は失敗扱いにせず「未検証」と明記する。

### 6.2 分類器の検証

全件表を確定する前に、章と種別を分散させた正例・負例を人手で確定する。
既存レポートをすでに読んでいるため完全な盲検とは主張しない。サンプルは
E0 / E1 / E2 / E3 / E5 / ENから2件ずつ層化固定選択し、既存レポートのS段階を
期待値に流用せず、本文の前後と実体から根拠を新しく記述する。

- 同一、コメント差、docstring差、真正な抜粋
- 演算子、境界値、例外、引数順、文順を変えた負例
- 演習、悪例、ライブラリ紹介、設定ファイル
- 1対多、多対1、章またぎ

期待結果との不一致が1件でもあれば分類規則を直して全件再生成する。
ゴールドセット自体が誤っていた場合は、期待値を黙って変更せず、根拠と変更履歴を残す。
